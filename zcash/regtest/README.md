# Isolated QPC Regtest services

`../../scripts/run-zcash-regtest.sh` is the single Linux command. It starts disposable, version-pinned `electriccoinco/zcashd:v6.20.0` and `electriccoinco/lightwalletd:v0.4.2` containers on an internal Docker network, creates private random local RPC credentials and owner-only temporary data, bypasses the image entrypoint and invokes `zcashd` directly with explicit Regtest flags plus a private config, runs `regtest_incoming`, emits its JSON evidence, and removes containers, network, volumes, credentials, and wallet database on exit. If startup or the test fails, the cleanup trap prints service diagnostics after redacting both generated RPC credentials. It never starts public-network peers or publishes RPC beyond host loopback. The full node config sets `regtest=1`, `connect=0`, `listen=0`, disables DNS discovery, and fixes Regtest upgrade parameters through NU6.2. The full-node service overrides the image entrypoint because the image entrypoint did not forward the Compose command in CI. Its direct daemon command and health check both explicitly require Regtest, and the adapter independently verifies node identity before scanning. There are no persistent volumes.

The incoming integration uses a process-local random test seed to derive a disposable shielded recipient. `zcashd` mines 101 local blocks, shields the disposable coinbase funds into its local Sapling wallet, constructs and proves an exact 0.5 ZEC shielded send to the test Unified Address, and mines its confirmation. The test requires `z_viewtransaction` to show the expected shielded output and amount, checks `gettransaction` confirmation metadata against `getblockhash` at the mined height, then requires the QPC wallet to discover a shielded note of the same amount. It closes and reopens the wallet database, rescans, and checks that received-output accounting is unchanged. This integration is not a separate process-restart test. The seed and spending key never leave the test process or appear in output. The production wallet API remains UFVK/view-only.

Full-node identity is obtained from authenticated `getblockchaininfo`: `chain` must equal `regtest`, every activation height supported by QPC's pinned `zcash_protocol` must match, and the node endpoint must be a literal loopback IP. Before scanning, the adapter also compares lightwalletd's latest compact-block hash to the full node's authenticated `getblockhash` at that height. This matters because the lightwalletd protocol exposes only `main`/`test` in `LightdInfo.chain_name`.

The compose images are amd64 images intended for compatible Linux Docker hosts and CI. Android/Bionic Termux is not a supported runner. The integration job in `.github/workflows/zcash-adapter.yml` runs the same script as local Linux users.

## Outgoing transaction boundary (not implemented)

The pinned backend delegates Sapling proof generation to the optional `zcash_proofs 0.30.0` implementation. Its `LocalTxProver::bundled()` uses bundled Sapling parameters; `LocalTxProver::from_bytes(spend, output)` accepts externally provisioned parameter files and validates them through that library. The Sapling circuit traits are `sapling_crypto::prover::{SpendProver, OutputProver}` (resolved as `sapling-crypto 0.7.0` here). Orchard has its own proving-key/circuit APIs in `orchard 0.15.5`; the Sapling `LocalTxProver` does not prove Orchard actions. Any deployment selecting Orchard therefore needs the matching Orchard proof backend and parameter/version verification.

The eventual boundary should have the view-only wallet create a proposal containing selected note references, receiver, value, fee, expiry, and network/branch identifiers; a separate signer receives an authenticated proposal and isolated spend capability, validates the proposal against wallet state, then returns a signed transaction plus a proposal digest. The wallet independently validates transaction network/expiry/outputs, broadcasts with lightwalletd, and confirms txid/mined block through the authenticated full-node RPC. Spending keys must never enter `WalletDb`, QPC's production wallet API, telemetry, or the proposal. This transaction builder, signer protocol, parameter file integrity manifest, and broadcast/confirmation path remain unimplemented; the current real incoming test uses zcashd's disposable test wallet only to create the inbound transaction.
