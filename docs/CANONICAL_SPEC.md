# QPC cross-L1 canonical authorization v1

## Normative encoding

The literal cross-language vector is [cross-l1-v1.json](fixtures/cross-l1-v1.json): `envelope`, `canonicalJson`, and `authorizationCommitment`. JavaScript exports `stringifyCrossL1AuthorizationEnvelope` (text), `canonicalCrossL1AuthorizationBytes` (UTF-8 bytes), and `computeCrossL1AuthorizationCommitment` (lowercase hex). Rust must match the literal text and hash, not a separately reserialized expected value.

1. Accept exactly the fields in the fixture, with the same nested object shapes; reject missing and unknown fields. Source and destination both require `nativeChainId`. No arrays, nulls, accessors, symbols, non-enumerable properties, custom object prototypes, or non-JSON values are accepted by the JavaScript object API.
2. `schema` is `qpc.cross-l1.authorization`; `version` is integer `1`. All names/IDs (including native chain IDs) match ASCII `[A-Za-z0-9][A-Za-z0-9._:/-]{0,255}`. Commitments are exactly 64 lowercase hexadecimal characters. String normalization is forbidden.
3. Atomic amounts, fee and nonce are strings matching `0|[1-9][0-9]*`, bounded by unsigned 128-bit maximum `340282366920938463463374607431768211455`. Source and destination amounts are positive. All numeric JSON fields are nonnegative integers no greater than `9007199254740991`; negative zero is rejected. Policy version is positive; decimals at most 255; slippage at most 10000 bps.
4. Require `issuedAtUnix <= notBeforeUnix < expiresAtUnix`. Authorization is valid at `notBeforeUnix`, invalid at `expiresAtUnix`. These are integer Unix seconds, not milliseconds.
5. Recursively sort object keys by ASCII lexical order. Emit JSON without whitespace or a trailing newline. All envelope strings are restricted to ASCII above, so there are no Unicode, escape, floating-point or locale ambiguities. Encode as UTF-8.
6. Compute SHA-256 over the UTF-8 bytes of `QPC-CROSS-L1-AUTHORIZATION-V1` followed by one NUL byte followed by the canonical JSON bytes. Emit 64 lowercase hex characters. The NUL is a single byte `00`, not the two characters backslash and zero.

## Native identities and scope

`networkId` is the human/protocol namespace (e.g. `near:testnet`); `nativeChainId` is the actual native identifier: NEAR `mainnet`/`testnet`, EVM unsigned canonical decimal `1`/`56`, Solana full base58 genesis hash, Zcash `mainnet`/`testnet`. Chain-specific adapters must pin and validate the relationship; the generic syntax validator does not prove it. Both fields are commitment-bound.

`agentIdentity.namespace/id/keyId` identifies the chain-native authenticated principal. For NEAR the configured namespace is `near` and `id` and `keyId` are the predecessor account ID. This is native predecessor authentication, NOT a signature, PQ signature, or proof of private-key possession provided by this module. A hash alone does not authorize anything.

The v1 action only carries `type` and `operation`; therefore adapters must restrict to exact supported native transfers and reject arbitrary calldata/instructions/approvals, whose parameters are not represented here. The amounts, assets, decimals, mapping, fee cap, slippage cap, recipient commitment, native chains, adapters, policy/version/commitment, revocation epoch and finality requirements all remain commitment-bound.

Replay domain key is SHA-256 of `QPC-CROSS-L1-REPLAY-V1` + NUL + compact JSON array `[authorityId,scope,source.networkId,source.nativeChainId,source.accountId,agentIdentity.namespace,agentIdentity.id]`. A nonce and an intent ID are each unique within that domain, independently of key ID and policy revision (rotation cannot reset replay protection). Consumed entries are never released by cancellation, expiry or failure.

## Settlement and local lifecycle

Future native settlement evidence must bind the exact authorization hash, destination network/native identity/adapter/asset, exact destination amount, recipient commitment, evidence class, transaction, inclusion reference, actual fee bounds and sufficient finalized confirmations. **No production verifier is implemented.** The generic boundary snapshots/freezes evidence and checks consistency, but returns `NOT_VERIFIED` even after a caller callback returns true. An RPC response, transaction hash or injected true result cannot promote an intent to settlement.

The currently usable local lifecycle is `CREATED -> AUTHORIZED -> SUBMITTING -> SUBMITTED`, plus `FAILED`, `CANCELED`, `EXPIRED` and `RECONCILING` paths. `CONFIRMED`/`SETTLED` are reserved historical/target states, not reachable production success: `confirm` rejects generic unverified evidence and `settle` always rejects, including legacy callback-created confirmations. `reserveSubmission` atomically enters `SUBMITTING` before any future external sender: only its single winning caller may send. `recordSubmission` stores a caller-reported transaction ID (it can also record an externally known submission from `AUTHORIZED`, but that reporting path alone is not an exactly-once sender or proof of execution). `CREATED`/`AUTHORIZED` can end `FAILED`, `CANCELED`, or `EXPIRED`. In-flight failures/timeouts and reorg reports enter `RECONCILING`; they cannot be canceled, expired or automatically re-sent. Future independently verified native recovery requires a separately reviewed integration; it is not supplied by revision checks or local state transitions.

The filesystem store is a local orchestration prototype, not a distributed database, consensus layer, executor, or chain proof system. See `agent-router/src/intent-store.mjs` for its explicit limitations. Its state record is not evidence that an external transaction happened. Cancellation/expiry are only allowed before submission. Uncertain submissions enter reconciliation rather than being retried or declared safely canceled. Finality loss after settlement is recorded as reconciliation, not silently ignored.

## Parsing boundary

The exported JavaScript API accepts data objects. Applications accepting raw JSON must use a parser that rejects duplicate keys before constructing those objects; `JSON.parse` alone discards duplicate keys and cannot provide that guarantee. The NEAR JSON ABI also receives `serde_json::Value`, whose parser retains the last duplicate key; it does not provide duplicate-key rejection. Raw JSON duplicate-key rejection is therefore NOT IMPLEMENTED at either ingress and must be supplied before parsing by a production gateway or a future strict ABI parser. Hashing and enforcement both use the same parsed object, but indexers with first-key semantics could disagree. The canonical object model itself never contains duplicate keys. Raw spellings such as `1.0` normalize to integer 1 in JS while Rust rejects that numeric representation; only canonical emitted bytes are the cross-language contract. Untrusted JavaScript executable proxies are outside this data API's threat boundary; do not invoke this API on code-bearing objects from an untrusted runtime.
