# QPC Agent Router — NEAR routes

This package is a local prototype for agent-operated payment routing: it includes a NEAR-to-Ethereum NEAR Intents 1Click path and a separate local-only NEAR-to-Zcash request builder. Tests use mocks; this is not a live-verified or deployed cross-chain payment service.

## Current scope

- Uses NEAR Intents 1Click for a NEAR-origin to Ethereum-destination route.
- Reads token identifiers from the live token catalogue; it never invents asset IDs.
- Requests an exact-input quote and validates amount, deadline, deposit address, and minimum output.
- Requires a QPC policy-gate callback before and after quote commitment.
- Builds an unsigned NEP-141 ft_transfer wallet transaction to the quote-specific NEAR deposit address.
- Submits the source transaction hash to 1Click and supports status verification.
- Requires independent destination-chain receipt verification before reporting SETTLED.

## NEAR to Zcash: local shielded request preparation only

The package also exports `computeNearToZcashPolicyArgsHash` and `buildNearToZcashShieldedDispatch`. These helpers build a deterministic, Testnet-only QPC `dispatch_action` payload for a single request with `privacy_class: "shielded"`, an opaque recipient reference, an exact ZEC amount, and a short expiry. The raw Unified Address is deliberately not accepted by this API.

The action argument hash must be configured in the QPC `ActionRule` for the exact request before dispatch. The helper returns 64-character hex; decode it to the 32 raw bytes expected by `ActionRule.args_hash`. Because the NEAR policy core's deposit caps measure attached NEAR, not ZEC, the exact argument hash is what binds this request's ZEC amount. This helper does not query the deployed policy, deploy or implement `zcash-router.near`, select a bridge/solver, resolve the private recipient reference, create or sign a Zcash transaction, or verify a Zcash receipt. The result is labeled `PREPARED_LOCAL_ONLY`; it is not a payment or settlement.

Only Zcash Testnet and the shielded privacy class are accepted. There is no transparent fallback. The opaque reference must be generated by a cryptographically secure random source and resolved only inside a separately secured Zcash adapter. Source-chain observers can still see the request metadata and amount.

Here, `privacy_class: "shielded"` is a request/policy label, not proof that a shielded transaction was constructed, broadcast, received, or made untraceable across the route.

### Adapter boundary for a future route provider

The package also exposes `submitNearToZcashDispatch` and `verifyNearToZcashRoute` as a deliberately explicit integration boundary. Submission requires both a caller-owned NEAR signer and a caller-supplied route provider; the package passes the opaque request and the NEAR transaction hash to that provider but does not select a solver, hold keys, or construct/broadcast a Zcash transaction. A provider `SUCCESS` status is converted to `SETTLED` only when `verifyNearToZcashRoute` receives an independent receipt verifier that returns `true`. Until a real audited `zcash-router.near` and adapter implement these callbacks, the route remains a mockable integration seam, not an end-to-end payment service.

Example preparation:

~~~js
import {
  buildNearToZcashShieldedDispatch,
  computeNearToZcashPolicyArgsHash,
} from "@qpc/agent-router";

const request = {
  paymentId: "pay-2026-0001",
  opaqueRecipientRef: "ref-7f2a9c8405d1b6e3f48a2d0c",
  amountZatoshis: "25000",
  expiresAtUnix: 1_800_000_300,
  nowUnix: 1_800_000_000,
  network: "testnet",
  privacyClass: "shielded",
};
const policyArgsHash = computeNearToZcashPolicyArgsHash(request);
const prepared = buildNearToZcashShieldedDispatch({
  ...request,
  qpcContractId: "qpc.testnet",
  policyId: "near_to_zcash",
  policyVersion: 3,
  requestId: "near-zcash-req-1",
  nonce: 7,
  actionId: "pay_zcash_shielded",
  zcashRouterAccountId: "zcash-router.testnet",
  policyArgsHash,
});
// Review/configure the exact QPC rule and obtain explicit wallet approval separately.
// This helper itself does not sign or submit prepared.qpcCall.
~~~

## Important security boundary

This package does not hold keys and does not sign transactions. A caller must supply an explicit NEAR wallet signer. The wallet remains responsible for key custody and transaction approval.

The policyGate callback is an integration seam, not proof that the current QPC NEAR contract already enforces this payment flow on-chain. The current QPC policy contract does not yet expose a dedicated escrow/payment-router method or token-balance accounting. Do not connect this package to an unattended production wallet until that on-chain enforcement is implemented and audited.

NEAR Intents 1Click is an external settlement provider. QPC does not operate the bridge, guarantee solver liquidity, or make the provider trustless. The agent must verify the destination receipt independently. Provider SUCCESS alone is not sufficient.

The NEAR-to-Ethereum route path supports NEP-141 source tokens to Ethereum destination assets only. The NEAR-to-Zcash helper only prepares a local request and does not settle it. Native NEAR payments, BSC, Solana, reverse routes, cross-chain escrow, and automatic retries are not implemented here.

## x402 exact-NEAR policy preflight (local-only)

`authorizeX402NearExactOffer` evaluates one x402 v2 `exact` offer against explicit local bounds for the NEAR network, NEP-141 token contract, recipient account, HTTPS resource origin, exact atomic-unit amount, and maximum timeout. It also requires the caller's policy gate to return `true`. This is a local preflight demonstration, not an x402 client/server or scheme adapter.

From this directory, run `node examples/x402-preflight.mjs` to see the fixture produce `POLICY_APPROVED_LOCAL_ONLY`. Run `npm test` to see the same helper reject unsupported schemes, networks, recipients, amounts, resource origins, timeouts, and denied policy decisions.

The helper does not create or verify a signed delegate action, check its on-chain nonce or block-height expiry, contact a facilitator, submit a transaction, or claim settlement. Its timeout check only caps the offer's `maxTimeoutSeconds`; it does not establish the expiry of a later signed payment. The on-chain QPC policy is not queried by this helper.

The published x402 NEAR `exact` scheme uses Ed25519 or secp256k1 signatures, not ML-DSA-65. It does not provide shielded-payment privacy, and an x402 offer must not be represented as proof of payment, a private route, or a post-quantum route. See the [x402 SDK feature matrix](https://docs.x402.org/sdk-features) and [NEAR exact scheme specification](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_near.md).

## Usage

~~~js
import {
  prepareNearToEthereumPayment,
  submitNearDeposit,
  getPaymentStatus,
  verifyPaymentStatus,
} from "@qpc/agent-router";

const prepared = await prepareNearToEthereumPayment({
  originAssetId: process.env.QPC_NEAR_ASSET_ID,
  destinationAssetId: process.env.QPC_ETH_ASSET_ID,
  amount: "1000000",
  recipient: "0x0000000000000000000000000000000000000001",
  refundTo: "agent.near",
  slippageTolerance: 100,
  policyGate: async (context) => qpcPolicyAdapter.authorize(context),
});

// Display prepared.sourceTransaction to the wallet approval UI.
// Only after explicit wallet approval:
const submitted = await submitNearDeposit(prepared, {
  nearSenderAccount: "agent.near",
  signAndSendTransaction: (tx) => nearWallet.signAndSendTransaction(tx),
});
~~~

## Tests

Run `npm test`. Tests use mocked API responses and wallet callbacks. They do not contact a live provider or x402 facilitator, sign transactions, verify settlement, or move funds.
